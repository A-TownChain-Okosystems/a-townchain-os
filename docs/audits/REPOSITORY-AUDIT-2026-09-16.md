## Findings

### F-20260916-ATCOS-001 — P1 — Documentation/Build Integration

**Class:** P1  
**Category:** correctness / documentation / integration  
**Family:** repository-architecture / build-system / workspace  
**Tags:** P1, a-townchain-os, cargo, workspace, documentation-drift, integration

`README.md` and `ARCHITECTURE.md` describe a root Cargo workspace and `scripts/sync_modules.py`, while the current tree places the Rust workspace at `kai-os/Cargo.toml` with 11 workspace members and no root `Cargo.toml` or `scripts/sync_modules.py` at the referenced paths. The root quick-start `cargo build --workspace` therefore does not match the current checkout. The architecture document also claims 19+ crates.

**Required correction:** make documentation and quick-start commands reflect the actual `kai-os/` workspace; remove claims for absent synchronization tooling; use the repository tree/manifests as authoritative.

### F-20260916-ATCOS-002 — P1 — Evidence Freshness

**Class:** P1  
**Category:** evidence / traceability  
**Family:** governance / audit / release-evidence  
**Tags:** P1, evidence, stale, bound-commit, traceability, SSOT

`.atc/evidence/evidence.yaml` is generated 2026-09-10 with `bound_commit: pending` and still summarizes a `Cargo-Workspace + sync_modules.py` state. It cannot serve as current commit-bound PASS evidence.

**Required correction:** bind the evidence artifact to the exact source commit only when generated by a verification run; until then keep tests/security/conformance explicitly unverified and remove stale implementation descriptions.

### F-20260916-ATCOS-003 — P2 — Generated File Register Drift

**Class:** P2  
**Category:** completeness / documentation  
**Family:** repository-inventory / governance  
**Tags:** P2, file-register, stale, generated, completeness

`FILE_REGISTER.md` claims 28 files and a small documentation-only tree, while the current repository contains the `kai-os/` Rust workspace, packaging, multiple workflows and additional specifications/docs. The register is stale.

**Required correction:** regenerate the register from the current Git tree or clearly mark it as historical. Do not use it as completeness evidence until regenerated.

### F-20260916-ATCOS-004 — P2 — Historical Test Counts

**Class:** P2  
**Category:** evidence / release-readiness  
**Family:** testing / governance  
**Tags:** P2, tests, historical-evidence, CI, release-gate

`STATUS.md` cites historical `106/106` test evidence and `docs/security/AUDIT-CHECKLIST.md` contains older expected counts, while current release readiness correctly remains `NOT_READY`. A fresh current-commit CI run is required before treating those counts as current verification.

**Required correction:** preserve historical results as historical and explicitly bind any current PASS count to a current commit/run.

## Security checks

Static searches performed for conflict markers, TODO/FIXME/HACK/XXX, `NotImplementedError`, `unimplemented!`, mutable checkout refs and `pull_request_target` returned no indexed matches in the repository search. The release workflow contains explicit Rust formatting, clippy, locked tests, RustSec audit, signed-release verification, SHA-256 checksums, SBOM and build provenance gates. These are controls, not proof of immunity to malware or compromise.

## Language / format assessment

- Rust is appropriate for the `kai-os` runtime/workspace and should remain canonical for native system infrastructure.
- Python is appropriate only for explicitly bounded tooling/validation where present.
- Cargo TOML, YAML, Markdown, PowerShell/ISS and Rust source match their respective roles; no blanket format migration is justified.
- The primary architectural correction is path/documentation truthfulness, not language migration.
